# Voyemu API

Скрипты управляют сеансами через Voyemu API, который обменивается объектами JSON: каждый процесс `voyemu test` читает один JSON-запрос со `schema: 1` и пишет один JSON-ответ в `stdout`, а диагностику — в `stderr`. Сетевой службы и MCP нет; причины — в записи [Voyemu API через `voyemu test`](../why/api.ru.md).

```sh
./voyemu test --request - <<'JSON'
{"schema":1,"request_id":"discover-1","op":"info"}
JSON
```

`--request FILE` читает запрос из файла; `-` или отсутствие опции — из `stdin`, не больше 128 КиБ. `info` возвращает версию и дату релиза Voyemu, схему, список операций установленной версии, экраны и ограничения.

## Запрос и ответ

| Поле запроса | Назначение |
| --- | --- |
| `schema` | Всегда `1`; иначе ответ — `TEST_SCHEMA` |
| `request_id` | Идентификатор, который выбирает клиент; по нему узнаётся повтор |
| `op` | Имя операции |
| `profile`, `session: {id}` | Профиль и сеанс; нужны запросам к сеансу |
| `session.ownership_id` | Подтверждение владения; нужно запросам, которые меняют сеанс |
| `machine` | Машина по имени каталога в `machines/` |
| `machine_path` | Путь к машине; только у `session.start` |

Ответ содержит `schema`, `request_id`, `operation_id`, `ok`, `elapsed_ms` и либо `result`, либо `error`. В ошибке есть `code`, `message`, `retryable` и `outcome`, см. [ошибки](errors.ru.md). Если запрос не удалось прочитать, `voyemu test` всё равно выводит JSON-ответ с ошибкой.

## Владение

`session.start` создаёт сеанс и возвращает его `id` и `ownership_id`. Менять сеанс может только запрос с верным `ownership_id`: ввод, питание, перезагрузки, значения автомобиля и остановка. `session.attach` даёт другому клиенту чтение без владения. У каждого запуска гостя своё поколение, поэтому клиент знает, какой запуск гостя он наблюдал.

## Квитанции

Voyemu регистрирует до выполнения каждое действие, снимок экрана и прогон `test.run`. Ключ состоит из области запроса, `request_id` и канонического содержимого запроса. Областью служит профиль для `session.start` и для `test.run`, который создаёт собственный сеанс, а для остальных запросов — их сеанс.

- Повтор того же запроса возвращает сохранённую квитанцию и не выполняет действие снова.
- Тот же `request_id` с другим содержимым завершается ошибкой `REQUEST_CONFLICT`.
- Повтор запроса, который ещё выполняется, получает `OPERATION_PENDING_UNKNOWN`, а повтор прерванного — `OPERATION_UNKNOWN`: операция в состоянии `pending` или `unknown` никогда не выполняется повторно сама.

`operation.get` читает квитанцию позже, например после аварийного завершения процесса клиента. Операция принимает ровно один способ поиска: `target: {operation_id: "32-hex-id"}` либо `target: {request_id: "original-id"}`; собственный `request_id` запроса относится к самому чтению. Результаты хранятся в `.local/build/automation`. Завершение процесса CLI не останавливает супервизор, поэтому исход может остаться `unknown`.

В завершённой квитанции (`receipt`) поле `outcome` следует из сохранённого ответа: `ok: true` даёт `completed`, `ok: false` сохраняет `error.outcome` (`not_started` или `unknown`), а нераспознанный ответ даёт `unknown`. `completed` значит, что команда завершилась, но не подтверждает видимого изменения UI. `unknown` не разрешает повтор. Отказ имеет `error.outcome: unknown` ровно тогда, когда `error.code` оканчивается на `_UNKNOWN`.

Результат `session.wait` тоже сохраняется, но, в отличие от действия, повторный запрос не сводится к сохранённому результату. Изменение с неизвестным исходом клиент не повторяет под новым `request_id`.

## Экраны и наблюдения

Операции обращаются к экранам по [роли экрана](../GLOSSARY.ru.md): `primary`, `secondary` или `cluster`, каждый 1920×720, а также к другим экранам машины, если они есть: `rear` размером 1902×540 у Free 6.11.1 и 7.3.1, а также `hud` размером 1280×720 у Passion. Роль — не номер слота SDK и не ID дисплея внутри гостя. `session.status` перечисляет экраны машины.

Ввод указателем принимает `screen`; наблюдение UI и снимок экрана — либо `screen`, либо список уникальных `screens`, но не оба поля сразу. Прежние имена `surface` и `surfaces` не принимаются. По умолчанию `session.ui` читает `primary`, `secondary` и `cluster`, а `session.screenshot` снимает `primary` и `secondary`; `rear` и `hud` запрашиваются явно.

| Экран | Снимок экрана | Дерево UI | Ввод указателем |
| --- | --- | --- | --- |
| `primary`, `secondary` | Да | Android | Касания, жесты, перетаскивание, селекторы и `expected` |
| `rear` | Да, вместе с остальными | Android | Простые касания и жесты в собственных пикселях экрана |
| `cluster` | Да | Kanzi, см. [дерево UI приборки](#дерево-ui-приборки) | Нет |
| `hud` | Нет, `TEST_UNSUPPORTED` | Нет, `TEST_UNSUPPORTED` | Нет |

Снимок экрана доказывает, что показал гость, но не успех сценария. `session.ui` читает дерево UI Android через наблюдатель UI в госте; узлы присоединённых окон показывают и текущее состояние `Drawable` — уровень и набор состояний изображения и фона, см. [наблюдения](#наблюдения). `session.wait` ждёт готовности или условия, а `session.watch.*` выдаёт события сеанса порциями.

Провайдеры — внешние процессы, которые `session.start` регистрирует по закреплённым файлам манифеста, не больше четырёх; их наблюдения появляются в `session.observe`. Кадры QNX доступны и по gRPC, см. [запуск и сеансы](launch.ru.md).

## Дерево UI приборки

Слот `cluster` в `session.ui` содержит дерево узлов Kanzi слоя Gauge. Встроенный в Gauge наблюдатель обходит дерево в потоке отрисовки сразу после успешной публикации окна Screen, вызывает только экспортированные функции Kanzi и записывает результат в закреплённую память гостя, откуда его читает хост. Каждый запрос заново читает эту память и ждёт подтверждения работы от того же источника, поэтому остановленный или перезапущенный Gauge старого дерева не вернёт.

```sh
./voyemu test --request - <<'JSON'
{"schema":1,"request_id":"ui-cluster-1","op":"session.ui","profile":"free-09-chinese-20260106-6.0.3","session":{"id":"SESSION"},"screen":"cluster","timeout_ms":5000}
JSON
```

| Профиль | Наблюдение |
| --- | --- |
| `free-09-chinese-20260106-6.0.3`, `free-11-chinese-20250710-6.11.1`, `free-11-chinese-20260731-7.3.1` | Текущее дерево Gauge: имена узлов, итоговые видимость и доступность, текст Kanzi, разрешённые видимость, доступность, непрозрачность и фактический размер каждого узла с явным статусом и окно Screen, после публикации которого снят снимок дерева |
| `passion-11-russian-20260403-2.1.4.80` | `status: "unsupported"`: у приборки Passion нет Gauge на Kanzi |

Размер и глубину дерева ограничивают бюджеты памяти и времени обхода. Прерванный обход возвращает префикс из целых узлов с отметкой `partial` и явной причиной. Весь JSON-ответ `session.ui` укладывается в общий бюджет 100 МиБ на все запрошенные экраны. Если часть узлов не помещается, ответ и затронутые экраны получают `partial` и `partial_reason: host_response_byte_budget`, а у оставшихся узлов сохраняются все нужные родители. Если бюджет превышают сами метаданные, ответ — `CLUSTER_UI_RESOURCE_LIMIT`. Ответ с недоступным источником после истечения срока может сохранить уже полученные небольшие наблюдения; он ограничен 64 КиБ и не делает новых запросов к гостю.

ID узлов действуют только внутри одного `observation_id`, поэтому узлы двух наблюдений клиент сравнивает по месту в сцене, а не по ID. Снимок дерева обновляется не чаще раза в 250 мс и только при публикации кадра; `freshness` показывает, была ли после него новая публикация. Поля и статусы описаны в разделе [наблюдения](#наблюдения).

## Общие правила

Операциям с сеансом нужна подготовленная машина с закреплёнными зависимостями; доступность источников и возможностей гостя зависит от платформы и машины. Изменениям нужен `session.ownership_id`, полученный при запуске с исключительным владением. Клиент проверяет готовность, `accepted` и статус условия: доставка команды не доказывает ожидаемый результат.

Сроки ожидания задаёт `timeout_ms`:

| Операция | `timeout_ms`, мс | По умолчанию |
| --- | --- | --- |
| `session.restart`, `multimedia.reboot` | 1..180000 | `180000` |
| `multimedia.power` | 1..90000 | `90000` |
| `multimedia.usb.attach`, `multimedia.usb.detach` | 1..25000 | `20000` |
| `session.ui`, `cluster.system` | 1..30000 | `5000` и `1000` |
| `session.screenshot`, `vehicle.can.get`, `vehicle.can.model`, `cluster.ipk.history`, `vehicle.mode.history`, `session.logs` с `android`, `anr` или `native` | 1..10000 | `5000` |
| `vehicle.can.history` | 1..15000 | `5000` |
| `session.wait` | 1..60000 | `10000` |
| `session.observe`, `session.watch.start`, `session.watch.read` | 0..60000 | `1000` |

## Сеанс

`session.start` принимает такие поля:

| Поле | Значения | По умолчанию |
| --- | --- | --- |
| `profile` | Профиль машины | — |
| `scenario` | `fresh` или `resume` | `fresh` |
| `boot` | Только `auto`; другое значение даёт `TEST_UNSUPPORTED` | `auto` |
| `with_cluster` | Запуск приборки | `false` |
| `seconds` | 1..3600, предел работы QNX при `with_cluster: true` | Без предела |
| `background` | Окно в фоне | `true` |
| `machine` | Каталог `machines/<machine>/`, манифест которого ссылается на `profile` | — |
| `machine_path` | Относительный или абсолютный путь к подготовленной машине, в том числе вне проекта | — |
| `providers` | До четырёх абсолютных путей к манифестам провайдеров | — |

`machine` и `machine_path` взаимно исключаются (`MACHINE_ARGUMENT`). Относительный `machine_path` отсчитывается от рабочего каталога процесса API, а манифест машины должен ссылаться на запрошенный `profile`. Сеанс создаётся с каноническим путём машины; ответ сохраняет `machine`, канонический `machine_seed` и `machine_manifest_sha256`. Поле `seconds` доступно и в `test.run.start`. Машина только с Android отвергает `with_cluster: true`.

Предварительная проверка допускает зарегистрированную переносимую машину до создания локальных параметров запуска: лаунчер проверяет манифест и привязки нужных инструментов хоста, затем активирует машину. `scenario` не выбирает Quick Boot: фактический режим показывает `session.status` в `deliveries`. Принудительного холодного старта вместо Quick Boot и режима с обязательным восстановлением снимка RAM нет.

`session.restart` перезапускает обоих гостей холодным стартом и сохраняет сеанс и владение. Ему нужны работающие Android и QNX с текущим межгостевым рукопожатием (handshake) и `expected_boot: {android: "Linux-UUID", qnx_generation: "positive-decimal", qnx_pid: 123}` из свежих наблюдений. Перед действием операция проверяет полномочия владельца и оба прежних запуска гостей. Завершение старых процессов и RAM QNX должно быть проверено; снимки RAM не восстанавливаются. Квитанция содержит `before`, `after`, исходные идентификаторы запроса и операции, `old_processes_stopped`, `guest_acknowledged` и `authority_retained`. Идентификатор QNX — типизированная запись собственного холодного старта `{kind: "owned_cold_incarnation", generation: "decimal", qemu_pid}` с новым рукопожатием гостя, а не выдуманный UUID QNX. Готовность Android и нужные подтверждения (ACK) UI, локали и нативных компонентов клиент проверяет отдельно.

Срок `session.restart` ограничивает ожидание клиента и проверки между стадиями остановки и запуска, у каждой из которых свой предел времени. Если срок истёк или ответ потерян, начатая стадия не отменяется, а новый перезапуск не разрешается. Для исходного действия клиент вызывает `operation.get` с тем же профилем, сеансом и владением. Дополнительные `runtime_receipt` и `runtime_outcome` позволяют прочитать надёжно сохранённый результат перезапуска после потери ответа IPC. Исходы `pending` и `unknown` и частичная смена гостей не означают завершения и не разрешают ни повтор, ни перехват владения. Клиент проверяет, что машина, сеанс, действие и загрузки обоих гостей совпадают. Внутри теста `test.run` операция запрещена; владелец вызывает её отдельным записанным действием.

`session.stop` проверяет, что его сеанс завершился и освободил ресурсы.

## Питание и перезагрузка

`multimedia.power` требует владения сеансом и логического поля `enabled` и запускает или останавливает только Android. Ответ содержит `enabled`, `changed`, `android_generation`, `android_pid` (`null` после остановки), `process_alive`, `verified`, `qnx_unchanged: true` и `source: "supervisor.android_lifecycle"`. Если операция остановила Android, `shutdown` подтверждает завершение обёртки и освобождение портов. Готовность приложений проверяется отдельно.

`multimedia.reboot` требует владения сеансом и `mode: warm` или `mode: cold`. `timeout_ms` ограничивает только ожидание клиента: истечение срока не отменяет перезагрузку, исход остаётся `unknown`, а автоматический повтор запрещён.

`cluster.power` и `cluster.reboot` требуют `expected_generation`, а `cluster.power` — ещё и `enabled`. Обе операции используют предел времени QNX, заданный при запуске сеанса.

## Профили и автомобиль

`profile.list` и `profile.get` сообщают, подготовлен ли профиль; это не подтверждает, что он запускается. `vehicle.fields`, `vehicle.get` и `vehicle.set` работают с входной моделью хоста, а не читают CAN через методы чтения гостя. `vehicle.fields` описывает каталог полей платформы запущенной машины с `session` или профиля, названного в `profile`, см. [модель автомобиля](vehicle.ru.md#модель-автомобиля); с `session` операция называет в `delivery` каждого поля гостей запущенной машины, которые его получают, см. [доставку гостям](vehicle.ru.md#доставка-гостям). `vehicle.set` требует `expected_revision` и `values`; сеанс проверяет связанные поля атомарно и задаёт поля, связанные с записанными. Ревизия передаётся числом JSON.

## Ввод

| Операция | Поля | Ограничения |
| --- | --- | --- |
| `input.tap` | `screen`, `x`, `y`; для серии — `count` и `interval_ms` | `x` не больше 1919, `y` не больше 719 и оба в пределах экрана; `count` 1..8 (по умолчанию `1`), `interval_ms` 0..300 (по умолчанию `100`) |
| `input.gesture` | `screen`, `points: [{x, y, at_ms}]` | От 1 до 64 точек; первая в момент `0`, остальные по порядку времени до 2000 мс |
| `input.drag` | `screen`, `from: {x, y}`, `to: {x, y}`, `duration_ms` | `duration_ms` 1..2000 (по умолчанию `300`); только экраны мультимедиа |
| `input.key.press` | `key` | Точные имена W3C из SDK |
| `input.wheel.press` | `button`, `hold_ms` | `hold_ms` 1..2000 (по умолчанию `100`) |
| `input.wheel.release` | — | Отпускает удержания владельца |
| `input.voice.trigger` | — | Нажимает кнопку голосового помощника |

Координаты указателя — пиксели исходного экрана; масштаб окна на них не влияет. Промежуточные перемещения жеста задаются явно: интерполяции нет. `input.drag` читает свежую геометрию и строит ограниченный жест с интервалами не больше 32 мс.

Нажатие по селектору требует `selector: {resource_id, package?}` и `expected: {boot_id, source_instance, revision, window, target}` из предыдущего наблюдения; селектор поддержан только у `input.tap`. Перед первым вводом свежее чтение проверяет идентичность цели, её геометрию и известные перекрывающие окна. Проверка не атомарна с доставкой нажатия и не доказывает, что окно принимает касания (`touchability: unknown`). Необязательный `expected` у `input.drag` тоже проверяет идентичность цели. У серии нажатий допуск проверяется один раз перед первым нажатием; неопределённую или частичную доставку повторять нельзя. `TEST_INPUT_CLEANUP_UNKNOWN` значит, что отпускание не подтверждено.

`input.gesture` с `expected` не требует `intent`: видимый и доступный узел с положительной геометрией после обрезки может принимать жесты без `clickable`. Проверки загрузки, источника, окна, цели и известных перекрывающих окон сохраняются. `target_basis: visible_enabled_geometry` не доказывает приём касаний или видимый результат. Необязательный `intent: scroll` или `intent: drag` сохраняет строгие требования `scrollable` или `clickable`. Требования `input.tap` и `input.drag` от этого не меняются.

`input.key.press` не гарантирует фокус. `Power` переключает штатное питание Android, `WakeUp` запрашивает пробуждение, `Standby` — сон. Завершение команды SDK не подтверждает изменение дисплея или ACC: клиент проверяет питание и CAN отдельно. Автоматической подмены `WakeUp` на `Power` и повторного ввода нет.

Удержание кнопки руля без продления истекает через 5 секунд. `input.voice.trigger` не передаёт распознанную речь. Ввода текста, буфера обмена и произвольных команд оболочки гостя нет.

### Отказ в допуске ввода

Отказ в допуске указателя может содержать `error.details`:

| Поле | Содержимое |
| --- | --- |
| `reason` | Обязательно: `boot_changed`, `source_changed`, `window_missing`, `window_changed`, `target_missing`, `target_ambiguous`, `target_changed`, `point_outside` или `coverage_unavailable` |
| `expected_window`, `observed_window` | Необязательно; только знаковые 32-битные целые поля `id`, `type`, `layer` и `bounds` (`x`, `y`, `width`, `height`) |
| `target_count` | Необязательно; число от 0 до 2147483647 |

Недопустимые поля проекции опускаются. Массивов и произвольных строк в подробностях нет, а в сериализованном виде они занимают меньше 512 байт. Диагностика берёт то же свежее наблюдение, не читая заново, и объясняет отказ в допуске, а не момент вывода пикселей или видимый результат. Поля `code`, `message`, `outcome` и `retryable`, правила доставки и повторов не меняются. Если цель не найдена или совпало несколько целей, ответ — `TEST_INPUT_BLOCKED`. Сохранённый результат, повторное чтение и `operation.get` сохраняют `details`.

## Приложения и телефон

`multimedia.launch` требует владения сеансом, `package` и текущего `boot_id`; `screen` по умолчанию — `primary`. Необязательный `component` должен принадлежать установленному пакету. Операция запускает приложение фиксированным вызовом ActivityManager, без произвольных команд оболочки и `Intent`. То, что команда принята, не доказывает, что интерфейс готов.

Действия `configure`, `connect`, `disconnect`, `incoming`, `answer` и `hangup` в пространстве `multimedia.phone` требуют владения сеансом. `configure` принимает `payload` с массивом `contacts` ровно из двух синтетических контактов `{name, number}` и необязательным `peer_name`. `incoming` принимает `payload: {number}`. Номер — `+7` и ещё десять цифр. Остальные действия принимают пустой `payload` или обходятся без него. `multimedia.phone.state` читает снимок телефона без владения сеансом. Доступность зависит от установленного адаптера машины.

## USB-накопитель

`multimedia.usb.attach` подключает [USB-накопитель](usb-drive.ru.md) к работающему мультимедиа, а `multimedia.usb.detach` отключает его; обе операции требуют владения сеансом и принимают только `timeout_ms`. Результат содержит `attached`, `changed` (`false`, если накопитель уже был в запрошенном состоянии), `android_generation` и `volume`. После изменения порта операция ждёт гостя до `timeout_ms`: `volume` — это `{uuid: "2026-1122", state}` с состоянием тома в `vold`, `mounted` после монтирования в Android, или `null`, если Android не показывает том накопителя. Если после подключения `volume` к концу ожидания равен `null` или ещё не `mounted`, Android не закончил; накопитель остаётся подключённым.

`USB_DRIVE` означает, что порт не изменился, например при выключенном мультимедиа; `USB_DRIVE_UNKNOWN` — что связь с эмулятором потеряна после отправки команды, и состояние порта проверяют через `session.status`, где его показывает `deliveries.android.usb_drive.attached`.

## Наблюдения

`session.ui` читает приборку и оба экрана мультимедиа параллельно за один `timeout_ms`. Результат `voyemu.session.ui.v1` всегда содержит `cluster`, `multimedia[0]` для основного экрана и `multimedia[1]` для второго; слоты вне выборки равны `null`. У каждого выбранного слота есть `screen`, `status`, `complete`, `nodes` и `windows`. Недоступный или неподдерживаемый источник возвращает пустые массивы. Ошибка чтения источника указывается в `error_code`, а при явном выборе экранов — ещё и в `error`. Общий статус `ready` значит, что ответ полон по всем выбранным экранам, `partial` — что есть хотя бы одно наблюдение, `unavailable` — что наблюдений нет. Чтения разных экранов не атомарны.

Если выбраны оба экрана мультимедиа, Voyemu читает их параллельно через наблюдатель присоединённых окон. Запросы с селектором или областью `interactive` используют отдельный режим наблюдения. С `scope` и `selector` запрос выбирает только экраны мультимедиа, и только явно. `scope` принимает `all_attached` и `interactive`; `interactive` нужны Android API30 и поддержка наблюдателя. `selector: {resource_id: "package:id/name", package: "package"}` возвращает до 64 совпадений на экран; `resource_id` обязателен, а `package` только уточняет выбор. `all_attached` может включать окна без привязки геометрии к экрану. Пустая выборка может быть полным наблюдением.

### Дерево Kanzi

Слот `cluster` читает текущее дерево узлов Kanzi слоя Gauge на Free 6.0.3, 6.11.1 и 7.3.1 с подходящими образами QNX и встроенным наблюдателем; у работающей приборки Passion в этом слоте `status: "unsupported"`. Наблюдатель внутри Gauge обходит дерево в потоке отрисовки сразу после успешной публикации окна Screen, не чаще раза в 250 мс, вызывает только экспортированные функции Kanzi и сцену не меняет.

| Поле | Содержимое |
| --- | --- |
| `id`, `parent` | Строки, действуют только внутри одного `observation_id`; у корня `parent: null` |
| `name` | Имя узла или `null`, если оно недоступно |
| `visible`, `enabled` | Итоговые значения с учётом предков |
| `properties.text` | Текст Kanzi узла: `{"status": "ok", "value": "..."}`, `{"status": "unset"}`, если значения у узла нет, или `{"status": "unavailable", "reason": ...}` |
| `properties.visible`, `properties.enabled` | Логические значения: `{"status": "ok", "value": ...}` или `{"status": "unavailable", "reason": ...}` |
| `properties.opacity`, `properties.actual_width`, `properties.actual_height` | Числа в той же форме |

Причины недоступности текста: `property_type_unavailable`, если образ не экспортирует такой тип свойства, `too_long` для текста длиннее 255 байт и `not_utf8`. Причины для остальных свойств: `property_type_unavailable`, `value_unavailable`, если значения у узла нет, и `non_finite_value` для NaN и бесконечности. Значение никогда не подставляется. Свойства содержат разрешённое значение Kanzi: оно может быть унаследовано или взято по умолчанию, поэтому `properties.visible` может быть `true` при итоговом `visible`, равном `false`.

`windows` содержит одну запись с `id: "0"`, `source: "qnx.screen"`, `binding: "posted_before_snapshot"` и `buffer_size` — окно Screen, после публикации которого снят снимок дерева. `selection_coverage` равен `gauge_node2d_tree`. Источник и время чтения описывают `source`, `source_clock_domain`, `host_interval`, `qnx_generation`, `sequence`, `observation_id`, `guest_monotonic_ns` (время снимка дерева) и `latest_present_guest_monotonic_ns`. `freshness` равен `latest_present`, если после снимка публикаций не было, и `older_than_latest_present`, если были: тогда дерево может расходиться с кадром на экране. Каждый запрос заново читает память гостя и требует, чтобы тот же источник подтвердил работу во время запроса; сам снимок дерева обновляет только следующая публикация, отсюда `observation: "last_sampled_present"`. Если приборка выключена или Gauge не подтвердил работу до истечения тайм-аута, слот содержит `error_code: "CLUSTER_UI_NOT_READY"`.

### Android

Супервизор читает наблюдатель Android через встроенный ADB и передаёт ответ по приватному IPC сеанса. Ответ наблюдателя в госте ограничен 6 МиБ. В ответе Android есть идентификаторы загрузки, дисплея и наблюдателя. ID узлов действуют только внутри наблюдения. У Accessibility и ViewServer разные ограничения, поэтому клиент проверяет полноту, достоверность геометрии, скрытие чувствительных данных и источник. Правила скрытия зависят от источника; клиент проверяет `text_redacted` и метаданные узла. Признак `actionable` не доказывает, что перекрытия нет или что анимация завершилась. Вложенные метаданные бэкенда частично сохраняют прежнюю форму.

У присоединённого источника ViewServer `enumeration_complete` значит, что все перечисленные окна прочитаны, а `metadata_complete` — что известны сведения о приватности и тексте узлов. Даже без ошибок чтения дерево с окнами и узлами может иметь `complete: false` из-за неизвестных метаданных; это не тайм-аут чтения дерева. Клиент проверяет `window_read_failures`, `unavailable_windows`, `selection_coverage` и `text_redacted`. Неизвестные метаданные не подтверждают, что текст доступен или что ввод не перекрыт.

Узлы присоединённого источника ViewServer содержат и текущее состояние `Drawable`: его читает поток UI приложения во время этого наблюдения. У узлов Accessibility этих полей нет.

| Поле | Содержимое |
| --- | --- |
| `image.drawable_status` | У узла `ImageView`: `available`, `none`, если `Drawable` нет, или `unavailable`, если чтение не удалось |
| `image.drawable_level` | Только при `available`: фактический `Drawable.getLevel()` |
| `image.drawable_state` | Только при `available`: возрастающие ненулевые ID атрибутов `Drawable.getState()`, например `16842913` для `android:state_selected` |
| `image.drawable_state_status` | `unavailable`, если набор состояний прочитать не удалось; уровень при этом остаётся верным |
| `background` | У каждого узла с `bridge_version: 1`: те же четыре поля для `View.getBackground()` |

Уровень никогда не подставляется: без чтения его нет, а статус равен `unavailable`. Эти поля возвращает запрос с обоими экранами мультимедиа без селектора или с явно выбранными экранами и `scope: "all_attached"`, например `{"schema":1,"request_id":"ui-1","op":"session.ui","profile":"PROFILE","session":{"id":"SESSION"},"screen":"primary","scope":"all_attached"}`. Уровни клиент сравнивает в том же окне и узле, а не через перестроенное окно по `resource_id`.

Наблюдению Accessibility основного экрана нужно хотя бы одно окно `TYPE_APPLICATION` с доступным корневым узлом. Набор только из системных окон отклоняется с `application_window_unverified`. В пределах исходного срока допускается одно повторное подключение с проверкой идентичности загрузки и сохранением блокировки снимка; если корня приложения по-прежнему нет, наблюдение отклоняется. Эта проверка не сверяет WindowManager с Accessibility полностью и не гарантирует, что найдёт каждое пропущенное окно.

### Поля редактора

Для редактируемого непарольного узла основного экрана Accessibility возвращает `hint` (строка), `showing_hint` (логическое значение), `selection_start` и `selection_end` (целые смещения в кодовых единицах UTF-16, `selection_unit: "utf16"`). Значение `-1` означает неизвестную границу. Узел сообщает `editor_status: "available"`; `selection_status` равен `"available"`, если обе границы неотрицательны, иначе `"unknown"`. Это значения Accessibility: положение курсора не выводится из фокуса или текста.

У парольного узла полей `hint`, `showing_hint`, `selection_start` и `selection_end` нет, а `editor_status` и `selection_status` равны `"redacted"`. У непарольного нередактируемого узла основного экрана и у узлов присоединённого источника ViewServer этих четырёх полей тоже нет, а оба статуса равны `"unsupported"`. Если метаданные редактора основного экрана недоступны, `selection_unit` равен `null`; ViewServer это поле не возвращает.

### CAN

`vehicle.can.get` опрашивает реальные методы чтения гостя, ACC и состояние транспорта. Поле `states` выбирает поддержанные перечисления (enum), включая `IVI_SOC_MODESET` и `HUM_VSP_FUNCTION_SW`; неизвестные значения отвергаются. `limit` принимает 1..32. Без `cursor` операция возвращает исходное состояние и текущий курсор. Для чтения истории запрос передаёт `cursor: {source_instance, after_seq: "decimal"}`; `after_seq: "0"` выбирает сохранённую историю с начала. Исходное нулевое значение сохраняется.

`vehicle.can.model` читает установленный наблюдатель модели CAN профиля Free 6.0.3 на поддерживаемых подготовленных машинах. Режим задаёт `mode: "snapshot"` (по умолчанию) или `mode: "drain"` с `limit: 1..32` и необязательным `cursor: {session: "decimal", next_cursor: "decimal"}` из предыдущего `terminal`. Все 64-битные значения передаются десятичными строками. Пропуск или потеря делают результат частичным; неизвестный, устаревший или переполненный курсор отклоняется. Чтение сырого кадра моделью не подтверждает приём ioctl, а попытка выдачи RX — доставку получателю. Пока установленный наблюдатель не подтверждён, операция недоступна.

Запись, применение и отложенная обратная связь — разные стадии. Binder UID сам по себе не идентифицирует приложение. Смену загрузки, службы и переполнение истории операции отмечают пропусками (`gaps`). Время Android с момента загрузки (elapsed time) и время получения на хосте идут по разным часам.

### Система

`multimedia.system` возвращает точечный снимок процессов (`PID`, `PPID`, `UID`, `name`) и сохранённую сводку `lastanr` и проверяет, что загрузка не изменилась. Поля `activities` и `services` содержат `status`, `items: [{user, component}]`, `complete` и границы чтения. Данные собирают фиксированные ограниченные команды `dumpsys`; `Intent`, их дополнительные данные (extras) и сырые строки исключены. Неизвестный формат, повреждённые записи и усечение дают `partial` или `unavailable`. Пустой результат подтверждает только явный штатный маркер. Если подисточник неполон, `value.complete` равен `false`. Если процесса нет в одном снимке, это не доказывает, что его не было всё время.

В поле `result.value.power` операция `multimedia.system` возвращает ограниченную диагностику питания Android: `status`, `complete`, `wakefulness` (`Awake`/`Asleep`/`Dreaming`/`Dozing`), `display_state` (`ON`/`OFF`/`DOZE`/`DOZE_SUSPEND`/`VR`/`UNKNOWN`) и логический `display_ready`. Отсутствующие значения — `null`. Неизвестный или неоднозначный формат даёт `unavailable`, неполные поля — `partial`. Сырой вывод не возвращается. Питание дисплея и ACC автомобиля — разные состояния.

`cluster.system` читает ограниченную диагностику приборки без владения сеансом. Ответ содержит `status: partial/unavailable`, `complete: false`, `qnx_generation`, `processes` и `gauge`. Доступный снимок включает только процесс Gauge: идентичность его источника, номер последовательности, метки счётчика активности (heartbeat) и времени гостя, число узлов и признак полноты сцены. Снимок доступен, только если счётчик активности продвинулся за время запроса. Если снимок недоступен, `gauge` равен `null`, а `reason` описывает причину.

### Источники и провайдеры

`session.observe` объединяет источники в `sources: {status, source_instance, boot_id, revision, value, host_interval}` и возвращает `complete`, `epoch` и `atomic: false`. Чтения координируются, но общий снимок не атомарен; `timeout_ms` ограничивает ожидание координатора.

`session.observe`, `session.watch.start` и `session.wait` с `condition` принимают `sources: [ID, ...]`. Без этого поля выбираются все зарегистрированные ID источников UI, CAN, системы и провайдеров. Пустой список, повторы и неизвестные ID дают `TEST_ARGUMENT`; порядок ID не важен. Ответ содержит только выбранные источники с их `status` и `coverage`. Если недоступен невыбранный источник, `complete` не меняется. Сборщики данных общие; спрос на них ограничен сроком чтения и подписки. Выбор подмножества источников не создаёт непрерывного покрытия.

Поле `session.start.providers` регистрирует до четырёх абсолютных путей к манифестам с закреплёнными обработчиком (worker), средой выполнения (runtime) и разрешёнными чтениями. Чтобы прочитать один провайдер, клиент передаёт `sources: [provider_id]` в `session.observe` и берёт `result.sources[provider_id]`. При ошибке провайдера его статус — `unavailable`. Voyemu сохраняет данные провайдера в `value`. Обработчик исполняет доверенный код от имени того же пользователя. Провайдеры входят в общее наблюдение и подписки по умолчанию, их покрытие имеет тип `sampled`.

### Логи

`session.logs` выбирает источник полем `source`, по умолчанию `supervisor`:

| Источник | Что возвращает |
| --- | --- |
| `supervisor` | До 64 КиБ или 128 структурированных событий, сведения о `gap` и число пропущенных записей; принимает `cursor: {file_id, offset}`, `details` запрещён |
| `android` | Метаданные логов Android; с `details: true` — ещё диагностический текст фиксированных тегов ART и нативного кода, до 2048 байт на сообщение, без учётных данных; `cursor` не поддержан (`TEST_UNSUPPORTED`) |
| `anr` | Сохранённую сводку ANR (включая `unknown`), ASCII-фрагмент до 16 КиБ без учётных данных, `excerpt_truncated`, `source_bytes` и `source_sha256`; `details` и `cursor` запрещены |
| `native` | Буфер сбоев `crash`, список файлов `/data/tombstones` и `handler_diagnostics`; `details` и `cursor` запрещены |
| `incidents` | События Android из журнала сеанса с курсором и ожиданием. Требует `system: "multimedia"` |

По логам нельзя доказать, что событий не было всё время.

`anr` проверяет, что `boot_id` не изменился. Источник использует фиксированную команду `dumpsys activity lastanr` и перечисляет обычные файлы `/data/anr` со стандартными датированными именами Android или `traces.txt`; произвольные пути недоступны. Он возвращает очищенный фрагмент до 16 КиБ из префикса размером не больше 131 071 байта. `captured_sha256` относится только к этому префиксу; `source_complete: false`. Выбор по имени и проверка текущей загрузки во время чтения не доказывают, что сохранённый стек относится к ней (`boot_association: unknown`). У снимка нет курсора, и он не даёт непрерывного покрытия. Ошибка чтения не значит, что ANR не было.

`native` читает сохранённый буфер `crash` (последние 512 строк, не больше 32 КиБ) и список обычных файлов `/data/tombstones`; необязательный `tombstone: "tombstone_00"` читает один файл (`00`–`99`) до 32 КиБ. Ответ содержит ASCII-текст без учётных данных, SHA-256 захваченного исходного префикса (`captured_sha256`), `captured_bytes`, `source_complete`, `excerpt_truncated`, найденные PID и время, текущие `boot_id`, `session_id` и `android_pid`. Текущая загрузка описывает сбор, а не происхождение старого файла аварийного дампа (tombstone), поэтому `boot_association` отмечает его как неизвестное. Недоступный каталог или файл отмечается как `unavailable`; права не расширяются, буферы не очищаются. `timeout_ms` ограничивает все чтения вместе.

Поле `handler_diagnostics` содержит до 128 первых совпавших строк из буферов `main`, `system` и `crash` с фиксированными тегами `libc`, `DEBUG`, `crash_dump32`, `crash_dump64`, `tombstoned`, `libdebuggerd_client`, `debuggerd` (все уровни), а также `IPCThreadState` и `ProcessState` (уровень предупреждения и выше); остальные теги выключены. Префикс ограничен 32 КиБ и ещё одним байтом, по которому видна обрезка. Действуют те же ограничения размера и времени, удаление учётных данных и проверки владения сеансом и неизменности загрузки. `collection_epoch` связывает сбор с сеансом, PID эмулятора SDK и загрузкой; принадлежность сохранённых строк этой загрузке не доказана. Произвольные теги и команды не принимаются. Это не непрерывный лог, и он не доказывает, что сбоев не было.

Снимки `anr` и `native` супервизор собирает через прямое подключение к `adbd` своего сеанса. До и после сбора клиент проверяет выбранную конфигурацию запуска, дескриптор SDK и подтверждение загрузки от супервизора. Супервизор проверяет PID эмулятора, принадлежность портов, имя AVD, идентификатор загрузки Linux и одноразовое значение (nonce) гостя. Гость, восстановленный из снимка, может сохранить прежнее одноразовое значение, если эти проверки проходят. `timeout_ms` ограничивает сбор всего снимка.

Для `session.logs` с `source: "incidents"` обязательно поле `system: "multimedia"`. Значение `system: "cluster"` возвращает `TEST_UNSUPPORTED`. Пропущенное или неизвестное значение возвращает `TEST_ARGUMENT`. Супервизор наблюдает за своим Android, пока тот работает. В журнал попадают необработанные исключения Java, фатальные сигналы нативных процессов, фрагменты стека debuggerd, сообщения Activity Manager об аварии и ANR. Журнал хранит нормализованные идентификаторы и ограниченные фрагменты стека. Сопоставленное уточнение приходит как запись `enriched` с тем же ID происшествия и увеличенной ревизией. У повторных аварий разные ID. Связь отдельного `am_crash` с другими записями может остаться неизвестной.

```json
{"schema":1,"request_id":"read-incidents-1","op":"session.logs","profile":"PROFILE","session":{"id":"SESSION"},"source":"incidents","system":"multimedia","limit":16,"timeout_ms":1000}
```

`limit` принимает от 1 до 32 записей, по умолчанию 16. `timeout_ms` принимает от 0 до 60000, по умолчанию 1000. Ноль возвращает ответ сразу. Чтобы продолжить с конца страницы, передайте `result.cursor` в следующем запросе. Запрос без курсора начинает с сохранившегося начала журнала. `head_cursor` показывает текущий конец для чтения последующих публикаций. Курсор содержит идентификаторы сеанса, системы и журнала (`stream_id`). Повторное чтение с тем же курсором может вернуть те же записи. Сохраните курсор после обработки страницы. Супервизор держит до 512 записей общим объёмом до 2 МиБ. `has_more` означает, что уже доступна следующая страница. При выходе супервизора журнал удаляется.

В записи указаны `boot_id` Android, поколение запуска SDK, затронутый процесс, время по часам гостя, причина и фрагмент стека. Порядок выдачи задаёт последовательность публикации. Поле загрузки вне списка записей относится к текущему подтверждённому гостю. Каждый читатель журнала Android начинает после начальной записи хвоста и сообщает о готовности этой границы. Так сохранённые до Quick Boot записи остаются за границей. При перезагрузке, потере наблюдения и вытеснении записей журнал сообщает о пропуске. Если курсор содержит прежний ID журнала того же сеанса, `cursor_reset` сообщает о смене, а новый курсор указывает на начало доступного окна. `sources` отдельно показывает доступность текстового потока и событий Activity Manager. Записи могут потеряться до начала наблюдения, при обрыве или внутри Android. Пустой ответ не доказывает отсутствие аварий.

## Подписки

`session.watch.start` принимает `condition`, `lease_ms: 1..60000` (по умолчанию `30000`), `timeout_ms` и `sources` — список уникальных зарегистрированных ID; без списка выбираются все источники. Ответ о готовности содержит `watch_id`, `epoch`, `cursor`, `baseline` и `result`. Клиент создаёт подписку до действия, которое нужно проверить.

`session.watch.read` принимает `watch_id`, `epoch`, `cursor`, `limit: 1..32` (по умолчанию `1`) и `timeout_ms`. `session.watch.stop` принимает `watch_id` и `epoch`. Результат явно сообщает об истечении подписки, пропусках и завершении. Длинный опрос (long polling) не удерживает блокировку сеанса. `TEST_WATCH_SIZE` отвергает слишком большой пакет, не подтверждая курсор.

Условие — дерево выражений:

| Операторы | Форма |
| --- | --- |
| `eq`, `count` | `{op, path, value}` |
| `present`, `absent`, `changed` | `{op, path}` |
| `all`, `any`, `ordered`, `first` | `{op, args: [...]}` |
| `stable`, `never` | `{op, condition, duration_ms}` |

`path` — указатель JSON Pointer внутри нормализованного состояния, например `/sources/can/value`; события лежат под `/event`. Пределы: глубина 16, 128 узлов и 4096 записей истории. Дочерние условия интервалов, `ordered` и `first` ограничены проверками состояния `eq`, `present`, `absent`, `count`, `all` и `any`. `changed` запоминает обнаруженное отличие. `ordered` требует разных последовательных событий. `first` принимает первую выполненную альтернативу, а при одновременном выполнении решает порядок `args`.

Статус условия — `passed`, `pending`, `failed` или `unavailable`. `baseline` описывает состояние, а не прошлое событие. Проверкам стабильности и отсутствия нужны непрерывное покрытие и отметка его границы (`watermark`); отдельные чтения не доказывают отсутствия записи, а пропуски запрещают принять результат.

`session.wait` с `condition` и поддержанными `sources` ведёт ограниченную подписку; клиент проверяет `result.status`, `gap` и `timed_out`. Вместо условия можно передать `predicate`: `session.reachable`, `android.ready`, `android.delivery`, `qnx.delivery` или `inputs.released`; для `delivery` нужна `revision` от 1 до 4294967295. Готовность транспорта не доказывает корректность сцены.

Подписка на UI сообщает покрытие `sampled_state_with_accessibility_notifications`. Уведомления Accessibility не гарантируют, что захвачено каждое краткое состояние, поэтому ими нельзя подтверждать непрерывное отсутствие в `stable` и `never`.

## Снимки экрана

`session.screenshot` принимает экран или список экранов, новый абсолютный `artifact_dir` внутри `.local/build/tmp` текущего проекта, `timeout_ms`, `max_skew_ms: 1..10000` (по умолчанию `500`) и необязательный `expected_generation`. Поле `rect: {x, y, width, height}` вырезает область одного экрана в исходных координатах. PNG и манифест содержат SHA, источник, интервалы чтения и результат проверки согласованности. Совместный снимок трёх экранов задают `screens: [primary, secondary, cluster]` и новый `artifact_dir`; `max_age_ms` в таком запросе не поддержан, потому что он предназначен только для Android.

Параллельные чтения проверяют, что сеанс, загрузка и поколение кадров не изменились, но вывод экранов не синхронизирован. Android не поддерживает положительный `after_sequence`, а приборка поддерживает. Для одного экрана Android `max_age_ms: 1..10000` проверяет оценку времени создания кадра SDK по часам Unix на момент получения с запасом 2 мс. Если системные и монотонные часы (realtime и steady) расходятся больше чем на 2 мс или метка нулевая либо в будущем, ответ — `TEST_FRAME_CLOCK`; если кадр старше предела — `TEST_FRAME_STALE`.

Эти проверки не доказывают момент вывода кадра внутри гостя или изменение пикселей. Новый запрос сам по себе не означает нового изображения. Снимок выключенной приборки отклоняется как `unavailable`. Артефакты, отклонённые из-за смены поколения или расхождения времён, сохраняются с `accepted: false`; потеря кадра не превращается в принятый частичный результат. Эталонные изображения, допуски и явное обновление эталонов задаёт сам тест.

`accepted` у снимка экрана подтверждает, что сеанс и поколение не изменились, а расхождение времён допустимо, но не подтверждает готовность ожидаемой сцены. Чёрный стартовый кадр или самопроверка приборки могут быть корректными снимками. Готовность UI и CAN и видимый результат проверяются отдельно; наличие файла или `accepted` эту проверку не заменяет.

### Снимок области по селектору

Для одного экрана Android `session.screenshot` принимает `selector: {"resource_id":"package:id/name","package":"package"}`; поле `package` необязательно. `selector` и `rect` нельзя передавать вместе. Контейнер выбирается по его собственному `resource_id`.

Операция делает полные свежие наблюдения UI до и после кадра SDK в пределах одного срока ожидания. Нужен ровно один видимый узел, который целиком помещается на экране; загрузка, источник, окно и геометрия цели не должны меняться. Выше цели не должно быть перекрывающего окна или окна с неизвестным слоем; `clickable` и `enabled` здесь не учитываются. Если привязка UI к дисплею не поддержана, снимок по селектору отклоняется, а снимок с фиксированным `rect` остаётся доступен.

Необязательный `expected` содержит `boot_id`, `source_instance`, `revision`, `window` и `target`, как для ввода; `revision` нужен для диагностики. Раздел `roi` манифеста сохраняет оба наблюдения и признаки `geometry_verified: true`, `atomic: false` и `pixels_match_node: false`. Атомарное соответствие UI пикселям и более новый кадр не гарантируются. Ограничения Android для `max_age_ms` и положительного `after_sequence` остаются прежними.

## Граница CAN при холодном перезапуске

Чтобы доказать режим OFF при холодном перезапуске, клиент читает `vehicle.can.history` в том же сеансе. Запечатанная вспомогательная программа на поддерживаемой нативной машине возвращает запись ядра с `producer: "closed_ecu_boundary"`, `capability: "closed_ecu_boundary_v1"`, целым `status: 0`, `session_id`, `owned_android_pid`, `guest_boot_id`, Linux `boot_uuid`, первым режимом и десятичными идентификаторами и счётчиками. Если доказательства нет, ответ содержит `status: "unavailable"` и `reason`.

Порядок перезапуска:

1. Прочитать `vehicle.can.history` в режиме OFF. Voyemu хранит до 16 подходящих снимков, поэтому историю читают непосредственно перед следующим шагом.
2. Отдельно получить заключительное наблюдение нативного приёма (RX) того же источника.
3. Вызвать `session.restart` с `expected_boot` и `expected_can: {anchor, native_terminal_boottime_ms}`.

`anchor` — весь неизменённый свежий результат `vehicle.can.history` в режиме OFF с пустыми очередями сырых и семантических операций и без незавершённой сырой операции. `native_terminal_boottime_ms` — положительная десятичная строка со временем нативного приёма строго после снимка. Перезапуск сам закрывает запись в источник. От снимка до остановки обоих гостей он проверяет режим OFF, пустые очереди, отсутствие незавершённой работы и неизменность счётчиков допуска сырых операций, переходов в ON и потерь. Квитанция `can_boundary` включает `anchor`, `native_terminal_boottime_ms`, `prepared`, `before_qnx_stop`, `before_android_stop`, `old_kernel_stopped` и `after`. После холодного старта перезапуск проверяет первый и текущий режимы OFF, нулевой глобальный счётчик ON и нулевые потери в новом ядре. Покрытие нативного приёмника и отрисованный PW проверяются отдельно.

## Прогоны

`test.run` выполняет список тестов в одном сеансе:

| Поле | Значения | По умолчанию |
| --- | --- | --- |
| `start` | `{profile, with_cluster, seconds, scenario, boot}` для нового сеанса | — |
| `profile`, `session` | Существующий сеанс вместо `start` | — |
| `cases` | `[{id, op, ...}]`, от 1 до 64 тестов с уникальными `id` | — |
| `artifact_dir` | Новый каталог артефактов | — |
| `artifact_budget_bytes` | 16777216..536870912 | `134217728` |
| `cleanup` | `stop` или `leave_running` | `stop` для нового сеанса, `leave_running` для существующего |

`start` и `session` взаимно исключаются. Прогону нужен подготовленный Android профиля, иначе ответ — `PROFILE_NOT_PREPARED`. Каждый тест получает `request_id` прогона, двоеточие и свой `id`. Первая ошибка останавливает прогон, остальные тесты получают `not-run`. Внутри тестов запрещены `test.run`, `session.start`, `session.stop`, `session.restart`, `session.attach` и `operation.get`. `passed` доказывает только перечисленные проверки.

Обычный порядок работы: `profile.get` → `session.start` → `session.wait` с `predicate: android.ready` → наблюдения и действия → `session.stop`. Клиент сохраняет владение сеансом и результаты операций. Тесты хоста используют подставные транспорты; загрузка гостей, UI второго экрана и диалогов, CAN, разрешения провайдеров и поведение приложений требуют отдельной проверки внутри гостя.
