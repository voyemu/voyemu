# Релиз

Релиз — одна версия лаунчера, упакованная для каждого хоста вместе с профилями той же ревизии. Рабочий процесс `release` собирает и публикует его по тегу, см. [CI](ci.ru.md#рабочий-процесс-release).

## Версия

Релиз задаёт версию и дату релиза вручную в одном месте — в `src/app/CMakeLists.txt`: `VOYEMU_VERSION`, например `1.0.0-beta1` или `1.0.0`, и `VOYEMU_RELEASE_DATE` в виде `YYYY-MM-DD`. Сборка не берёт их ни из коммита, ни из времени сборки. Версию сообщают `voyemu --version`, панель «О программе» [окна](../how/window.ru.md) и операция `info` [Voyemu API](../how/api.ru.md); панель «О программе» показывает дату релиза на языке интерфейса, а `info` возвращает её как `release_date`. Ту же версию используют имена архивов, формула Homebrew и примечания к релизу. Тег релиза — `v` и та же версия, например `v1.0.0-beta1`.

Версия с суффиксом после `-`, например `1.0.0-beta1`, — предварительный релиз: рабочий процесс `release` публикует его как предварительный релиз GitHub и не меняет формулу Homebrew. Версия без суффикса, например `1.0.0`, — стабильный релиз, который обновляет и формулу. Примечания к релизу — раздел версии в `CHANGELOG.md` под заголовком `## <version>` или `## <version> — <date>`.

Отправка тега стабильного релиза запускает рабочий процесс автоматически. Предварительный релиз запускается вручную на его теге. Параметр `macos_only` или `windows_only` публикует архив одного хоста; без обоих параметров публикуются архивы всех хостов.

## Архивы

| Хост | Архив |
| --- | --- |
| macOS arm64 | `voyemu-<version>-macos-arm64.tar.xz` |
| Linux x64 | `voyemu-<version>-linux-x64.tar.xz` |
| Windows x64 | `voyemu-<version>-windows-x64.zip` |

`SHA256SUMS` рядом с ними перечисляет их SHA-256. Каждый архив содержит один каталог `voyemu-<version>/`:

| Путь | Содержимое |
| --- | --- |
| `voyemu` или `voyemu.exe` | Лаунчер: CLI, супервизор, окно и графический обработчик |
| `profiles/` | Все профили ревизии лаунчера |
| `notices/` | Лицензия Voyemu, сторонние лицензии и `dependencies.lock.json` |
| `README.md`, `CHANGELOG.md`, `SECURITY.md`, их русские версии и `LICENSE` | Тексты корня проекта |

Оригиналы и образы, полученные из них, в релиз никогда не входят.

## Корень установки

Распакованный каталог — корень установки: `deps`, `fetch` и `build` создают в нём `.local/` и `machines/`, см. [корни `.local`](../how/local-roots.ru.md). Лаунчер выбирает корень по собственному расположению, поэтому командам не нужен параметр корня. Он берёт первый подходящий вариант:

1. Каталог лаунчера, если в нём есть `profiles/` или `.local/`, как в распакованном архиве.
2. Ближайший каталог выше лаунчера, в котором есть `profiles/` и `src/app/`, — рабочая копия исходников.
3. Рабочий каталог, если в нём есть `.local/`.
4. На macOS — `~/Library/Application Support/Voyemu`.

## Файлы проекта

`deps`, `fetch`, `build` и `check` читают содержимое нескольких файлов дерева исходников: пины `src/app/toolchain.json` и `src/prepare/`, скрипты гостя QNX, настройку экранов и раскладки MCU из `src/guest/qnx/`, маршруты кнопок руля и заставку. `src/app/project_files.cmake` при сборке встраивает в лаунчер копии ровно этих файлов; корень с `src/` читает своё дерево, установка без `src/` — копии. Во время сеанса адаптер приборки в обоих случаях берёт раскладки MCU из копий. Помощник Java получает манифест инструментов в запросе, а исходники помощника AudioPolicy — из своего JAR.

Без `--jdk` подготовка использует закреплённые ресурсы помощника и гостевого кода Java даже в рабочей копии исходников. Если ресурс помощника недоступен, подготовка завершается с `JAVA_HELPER_ASSET_MISSING`, не запуская сборку из исходников. В рабочей копии исходников `--jdk PATH` выбирает рецепт разработчика; ключ его кеша учитывает фактические исходные файлы, см. [CI помощника Java](ci.ru.md#рабочий-процесс-java-helper). Подготовленные машины сохраняют контрольные суммы встроенных файлов, а не проверки совместимости с текущими авторскими исходниками. Подготовка по-прежнему обнаруживает изменение входов во время операции и проверяет внешние пины и выходные артефакты. Рецепты сборки ресурсов CI из исходников работают в рабочей копии исходников.

## Сборка архивов

```sh
cmake --install .local/build/native --component Runtime --prefix "$PWD/.local/build/stage"
src/dev/release/archive.sh 1.0.0-beta1 linux-x64 .local/build/stage .local/build/release
```

Компонент установки CMake `Runtime` содержит лаунчер, `notices/` и графику окна из `profiles/common/`. `archive.sh VERSION HOST STAGE OUTPUT` берёт из него лаунчер и `notices/`, добавляет отслеживаемые файлы `profiles/` и тексты корня и записывает архив хоста `HOST` с файлом `.sha256` в `OUTPUT`. Записи отсортированы, у каталогов режим 755, у файлов 644, у лаунчера 755, владелец и группа 0, а время каждой записи — 00:00 UTC даты `VOYEMU_RELEASE_DATE` из коммита HEAD или `SOURCE_DATE_EPOCH`, если он задан, поэтому повторный запуск даёт те же байты. Скрипт работает на Linux с git, GNU tar и xz; для zip под Windows нужен инструмент `jar` закреплённого JDK, путь к которому задаёт `JAR`. Тест CTest `release_archive` дважды собирает архивы Linux и Windows, сравнивает их, проверяет состав и запускает распакованный лаунчер Linux без `src/`.

## Homebrew

На macOS arm64 и Linux x64 `brew install voyemu/tap/voyemu` устанавливает архив своего хоста из последнего стабильного релиза. Формула — `Formula/voyemu.rb` репозитория `voyemu/homebrew-tap`; `src/dev/release/homebrew/voyemu.rb.in` — её шаблон, а `src/dev/release/homebrew.sh VERSION REPOSITORY SHA256SUMS OUTPUT` подставляет версию, адреса архивов и их SHA-256. Формула хранит лаунчер и `profiles/` в своём каталоге (keg) и после каждой установки копирует их в `var/voyemu` префикса Homebrew; `bin/voyemu` ссылается на эту копию, поэтому `var/voyemu` становится корнем установки, а его `.local/` и `machines/` сохраняются при обновлениях. Тест формулы запускает `voyemu --version`.

## Ресурсы релизов
